# ADR-002: 采用「.NET sidecar (Tier1) + Rust 直调 HID (Tier2)」双通道通信架构

## Status
Accepted (2026-10-16)

## Background
原版驱动为**双通道**控制模型，两类控制面走完全不同的 Windows 机制：

- **APO 通道**：EQ、空间音频（Xear Surround Headphone / Speaker Shifter）、降噪、AI 音效等，写入 Windows 音频 **APO PropertyStore**（注册表 `FX\0\<context>\User` 下的 PKEY，见 CM002X1_Ext.inf 中 `CAPXSFX/CAPXMFX/CAPXEFX_PROPERTYSTORE_CONTEXT`）。
- **HID 通道**：LED 灯效、设备级控制、固件信息、耳机电池/头动等，走 USB HID 报告。

厂商通过 `CmXearSDK.dll` / `CmHidra.dll` / `CmDevite.dll` / `cmgaieochos.dll` / `CmResoDots.dll` / `cmtekea.dll` / `CmJokkoo.dll` / `CmFirmwareUpdateSDK.dll` 对这些通道做了一层封装。

Tauri（Rust）方案必须选择：是全部用 Rust 重新实现双通道，还是复用厂商 DLL。

## Decision
采用**混合双通道**架构：

- **Tier1 — .NET 8 sidecar（授权复用厂商 DLL）**：
  - 承载对 APO PropertyStore 与 HID 的厂商封装调用，优先复用 `CmXearSDK.dll` / `CmHidra.dll` / `CmDevite.dll`。
  - 以独立进程运行，Tauri 通过 stdin/stdout（JSON-RPC 行协议）通信，隔离厂商 DLL 的崩溃与位宽问题（厂商 DLL 多为 x86/x64 native，.NET 8 x64 宿主最稳）。
  - **前置校验（强制）**：接入前必须①反查各 DLL 导出的符号表确认调用面稳定；②确认厂商（C-Media / 竹林鸟）再分发授权。未完成前 Tier1 标记为 BLOCKED，不得进入实现。
- **Tier2 — Rust `windows` crate 直调 hid.dll**：
  - 使用 `windows` crate 的 Win32 API（SetupDi 枚举 + `CreateFile` 打开 HID + `HidD_GetPreparsedData` / `HidP_*` 解析报告描述符 + `WriteFile`/`ReadFile`）直连 HID。
  - 作为 Tier1 不可用（未授权 / DLL 缺失 / 异常）时的**回落通道**，至少保证设备枚举、设备信息、LED 基础读写可用。

Tauri command 层按「能力」而非「通道」暴露接口；后端路由按能力选择 Tier1 优先、Tier2 回落，并在返回中携带 `channel` 与 `tier` 元数据。

## Consequences
正面：
- 最大化复用厂商已验证的控制逻辑，降低逆向风险与开发成本。
- 进程隔离，厂商 DLL 异常不会拖垮 UI。
- Tier2 保证即使无法复用 DLL 也能提供基础功能。

负面：
- 引入 sidecar 进程生命周期管理（启动、健康检查、崩溃重启、结束清理）。
- sidecar 增加分发包体积，并需处理 .NET 运行时（可考虑 self-contained 或 runtime-dependent 取舍）。
- 依赖厂商 DLL 的**授权**与**符号稳定性**，存在明确前置风险项。
